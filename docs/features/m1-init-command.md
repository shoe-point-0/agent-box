## Technical approach

- Keep `init` entirely in the Machine-side CLI dispatch path. It resolves only the current directory and never asks for daemon paths, constructs a daemon client, starts `aboxd`, or invokes Git/runtime tooling.
- Emit one constant, deterministic `v1alpha1` starter document at `.abox/box.yaml`. The local repository source is `..`, so strict-loader validation resolves it to the directory in which `abox init` runs without inspecting Git or requiring a Compose file to exist.
- Default creation uses an exclusive file create so an existing manifest wins even if it appears after the initial check. `--force` is the only overwrite path and uses the repository's crash-consistent atomic writer, which refuses symbolic-link and non-regular destinations.
- Create `.abox` with owner-only permissions when absent, write the manifest owner-only, and remove a newly-created empty directory if manifest creation fails. Cover exact deterministic bytes, strict-loader acceptance, refusal/forced replacement, hostile destinations, argument handling, and a filesystem/daemon-boundary assertion in CLI tests.

## Outcome and follow-ups

Implemented `abox init` as a local-only CLI command. It writes a deterministic strict starter manifest using exclusive no-clobber creation by default, exposes the sole overwrite path as documented `--force`, and uses crash-consistent atomic replacement for that explicit path. It rejects symlinked manifest directories and symbolic-link or non-regular overwrite targets. No daemon connection, user state path, Git process, runtime host, Box state, or network allocation is involved.

The starter intentionally uses stable generic names and points its sole local repository source at `..`, making it loader-valid from every real working directory without guessing project metadata or requiring Git inspection. Service existence and the authored `compose.yaml` remain normal planning-time concerns after the user edits the starter.
